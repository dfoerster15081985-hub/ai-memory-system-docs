## 1. Leitprinzip

> **Live Mode arbeitet mit dem User an Quantitaet.**
> **Deep Mode arbeitet allein an Qualitaet.**
> **Alles andere folgt daraus.**

> **Live muss schnell sein. Deep muss effizient sein.**
> **Deep laeuft autonom, soll aber in der verfuegbaren Zeit**
> **so viel Qualitaet wie moeglich schaffen - kein egal wie lang.**

Daraus leiten sich alle weiteren Konzepte ab.

## 2. Live/Deep Mode

### Live Mode
- Ziel: Quantitaet, schnelle Iteration
- User im Loop
- Kleine Modelle, kurze Runden (1-2 Min)
- Nur verifizierte Quellen
- Cloud optional

### Deep Mode
- Ziel: Qualitaet, autonome Arbeit
- Kein User
- Grosse Modelle, lange Runden (5-15 Min)
- Alle Quellen inkl. unverifiziert
- gamemoded aktiv, KDE pausiert
- Thermik ueberwacht

### Trigger
- Manuell (UI-Button)
- Inaktivitaet (5 Min)
- RTC-Wake (03:00)
- Rueckkehr: User-Input

### Sync-Punkt
Am Ende jeder Runde:
- Was ist fertig?
- Was fehlt?
- Konflikte aufloesen
- Naechste Runde planen

### Deep-Mode-Ausstieg (Nachtrag 2026-10-03)

Deep Mode endet nicht nur durch User-Input. Drei Ausstiege:

1. **Erfolg:** Alle Aufgaben erledigt -> Sync-Punkt -> warten auf User.
2. **Konflikt:** Widerspruch nicht aufloesbar -> Zustand speichern -> User benachrichtigen.
3. **Budget:** Rundenlimit oder Zeitlimit erreicht -> Zwischenstand -> User entscheidet.

**Konflikt-Resolution:**
- Widerspruch zwischen zwei Quellen: hoehere Autoritaet gewinnt (Tier-System §6).
- Widerspruch zwischen Quelle und Konzept: Konzept gewinnt, Abweichung dokumentieren.
- Unloesbarer Widerspruch: Deep Mode pausiert, schreibt Frage in Sync-Punkt.
- User-Input ist immer moeglich (Barge-in auch im Deep Mode).

**Was nicht passiert:**
- Deep Mode entscheidet nie gegen das Konzept.
- Deep Mode loescht nie ohne Backup.
- Deep Mode bricht nie mitten in einer Transaktion ab (Snapper-Punkt abwarten).

## 4. Task Splitting + Adaptive Groesse

### Kernidee
Aufgabe wird in Teilaufgaben zerlegt, jede mit eigener Groesse.
Ziel: alle Agenten zur selben Zeit fertig (Makespan).

### Statisches Splitting (erste Umsetzung)
Nach task_type:

| Aufgabe-Typ | Schritte | Rollen |
|---|---|---|
| Coding | 4 | Repository, Architecture, Implementation, Test |
| Recherche | 3 | Evidence, Source-Critic, Synthesizer |
| Test | 1 | Test/Validation |
| Doku | 2 | Repository, Implementation |

### Dynamisches Splitting (nach 20-30 Runs)
Experience Store liefert Schaetzung:
- task_type + model_id -> durchschnittliche duration
- Splitting-Algorithmus verteilt Schritte so, dass alle Agenten gleichzeitig fertig werden
- Formel: `chunk_size = total_estimate / n_agents * speed_factor`

### Lernen
Experience Store merkt sich:
- task_type + model_id + duration
- Nach 20-30 Runs: belastbare Schaetzung
- Rundenlaenge wird dynamisch angepasst

### Makespan-Regel
- Schnelle Agenten: kleine Haeppchen
- Langsame Agenten: grosse Bloecke
- Ziel: alle zur selben Zeit fertig
- Bei Ueberlast: Lead splittet neu

### Was der Lead entscheidet
1. Welcher task_type? (Coding, Recherche, Test, Doku)
2. Welche Rollen? (aus §5-Tabelle)
3. Statisch oder dynamisch? (erste 20 Runs: statisch)
4. Sync-Punkt setzen.

## 5. Coding-Orchestrator

### Struktur
Der **Lead** koordiniert. Er zerlegt die Aufgabe, waehlt Rollen,
setzt Sync-Punkte. Die **6 Spezialisten** arbeiten.

Lead ist keine Rolle in der Tabelle - er ist die Instanz,
die die Rollen aufruft.

### Sechs Spezialisten-Rollen

| Rolle | Toolset | Profil | Refl. | Output | Darf nicht |
|---|---|---|---|---|---|
| Architecture | read_file, list_files | skeptic=0.90, fals=0.85 | 3 | Design-Doc | schreiben, ausfuehren |
| Repository | read_file, list_files, grep | evidence=0.98 | 2 | Struktur-Karte | schreiben, ausfuehren |
| Implementation | read_file, create_file, run_file | skeptic=0.30 | 1 | Code-Dateien | run_command |
| Debugging | read_file, run_file, run_command | skeptic=0.90, fals=0.85 | 3 | Root-Cause + Fix | create_file |
| Autocomplete | create_file (append) | keine | 0 | Snippet | lesen, ausfuehren |
| Test/Validation | read_file, run_file, run_command | skeptic=0.95, fals=0.90 | 4 | Test-Resultat | create_file |

**Toolset-Regeln:**
- Jede Rolle hat **nur** die Tools, die sie fuer ihre Aufgabe braucht.
- `run_command` ist **nicht** universell. Nur Debugging und Test/Validation.
- `create_file` ist **nicht** universell. Nur Implementation und Autocomplete.
- Der Lead entscheidet, welche Rolle den naechsten Schritt macht.

**Profil-Regeln:**
- `skeptic` steuert, wie stark die Rolle eigene Vorschlaege anzweifelt.
- `fals` steuert, ob aktiv nach Gegenbeispielen gesucht wird.
- `evidence` gewichtet Quellen gegen Intuition.
- Refl. (Reflexionstiefe, §8) steuert, wie tief Fehler analysiert werden.

**Warum die Trennung wichtig ist:**
- Architecture kann nicht schreiben -> kein Copy-Paste-Code.
- Implementation kann nicht `run_command` -> kein Systemeingriff.
- Debugging kann nicht `create_file` -> Fix kommt ueber Implementation.
- Test/Validation kann nicht `create_file` -> keine Self-Certification.
- Autocomplete kann nicht lesen -> kein Kontext-Diebstahl.

### MoE-Router/Prefetch (separate Ebene)
Der MoE-Router ist **kein Agent**. Er ist ein Mechanismus im Modell.
Er gehoert nicht in diese Tabelle, sondern in MOE_ARCHITEKTUR.md.
Agent-Ebene (Lead + 6 Rollen) und Modell-Ebene (MoE-Router)
sind sauber getrennt.

### Reihenfolge pro Aufgabe
1. Lead: Aufgabe zerlegen, Rollen waehlen
2. Recherche-Phase (2 Min) - Rolle: Repository
3. Analyse (3 Min) - Rolle: Architecture
4. Implementierung (5 Min) - Rolle: Implementation
5. Test (2 Min) - Rolle: Test/Validation
6. Sync-Punkt - Lead sammelt Ergebnisse

## 10. Datenbank-Standard (aktualisiert 2026-10-04)

### Engines (verbindlich)

Drei Engines, alle embedded, kein Server:

| Engine | Rolle | Wo |
|---|---|---|
| SQLite + FTS5 | Kern (relational, Volltext, Rohdaten-Append) | SSD Hot |
| KuzuDB | Graph + Vektor (HNSW integriert) | SSD Hot |
| DuckDB | Deep-Mode-Analyse (liest SQLite, kein Live-Store) | SSD Hot, Scans auch HDD |

Verworfen: LanceDB (KuzuDB uebernimmt Vektor), Neo4j (Server).

### Ziel-Schema (SQLite + FTS5)
id, source, source_type, authority, license, license_ok,
content, content_zst, tokens, language, ecosystem,
version, date, source_url, checksum, tags, created_at,
meta_level, confidence, verified_at, conflicts_with, supersedes

### Meta-Ebenen (nullable, nur Deep fuellt)

Zwei Bereiche, Live-`raw` ist Input fuer Deep:

- **Content:** raw -> derived -> verified / conflict -> archived
- **Telemetry:** raw -> aggregated -> pattern / recommendation -> archived

Ein Eintrag kann mehrere Meta-Ebenen tragen (Zeitverlauf).

### Live-Schreiben (minimal)

Pflicht: id (auto), content, source, created_at, meta_level="raw".
Optional: source_type, language, tags.

### Deep-Schreiben (streng)

Erweitert meta_level. Pflicht je Ebene:
- confidence (bei derived/verified)
- verified_at (bei verified)
- conflicts_with (bei conflict)
- supersedes (bei Versionierung)

### Konflikt- und Versionsregeln

- **Nichts wird ueberschrieben.** Alles wird versioniert.
- Widerspruch erzeugt neue Zeile mit `conflicts_with=<id>`.
- Update erzeugt neue Zeile mit `supersedes=<id>`, alte Zeile wird `archived`.
- Beim Lesen greift §2 (Konflikt-Resolution, Tier-System).

### Speicher-Tier-Logik

| Meta-Ebene | Tier | Medium | Live | Deep |
|---|---|---|---|---|
| raw | Hot | SSD | rw | rw |
| derived | Hot | SSD | r | rw |
| verified | Hot | SSD | r | rw |
| conflict | Hot | SSD | r | rw |
| archived | Cold | HDD | r | w |
| latent nuetzlich | Warm | SD | r | w |

**Regel:** `archived` geht immer auf die HDD. Keine Zwischenstufe.
SD ist Lese-Archiv fuer seltene, aber nuetzliche Daten.
Live liest, Deep schreibt - auf SD und HDD.

### Komprimierung
- Datei-Ebene: zstd-19
- Aktive DB: SQLite, FTS5, keine Inhaltskompression
- Kalte Daten: ausgelagert + zstd

### Chunk-Strategie
- Python Docs: 800 Token (Funktion pro Chunk)
- PyPI: 200 Token (strukturiert)
- OSV/CVE: 400 Token (pro Advisory)
- Stack Overflow: 1500 Token (Q+A zusammen)
- Code: 400 Token (Funktion/Klasse)

### Regel
> Original dient als Eingang, nicht als Lager.
> Nach Standardisierung wird das Original geloescht.

Ausnahmen: Dash/Zeal-Docsets, Lizenz-Auflagen, Verifikation.

- Alles aus A4
- Komplette Stack Exchange
- Kompletter Code-Corpus
- gpt-oss-120b mit vollem Kontext moeglich
- SD komplett belegt
- Hardware-Grenze: NVMe (238 GB) + SD (476 GB) = 714 GB

### Hardware-Realitaet (aktualisiert 2026-10-04)

| Speicher | Nominal | Linux | Anschluss | Rolle | DB? |
|---|---|---|---|---|---|
| Interne NVMe | 256 GB | 238 GiB | PCIe | System, Code, Config, aktive Modelle | NEIN |
| SD (Deck-Slot) | 512 GB | 476 GiB | microSD intern | Warm-Tier, latent nuetzlich | JA |
| Externe SSD | 256 GB | 238 GiB | USB | Hot-Tier (aktive DB) | JA |
| Externe HDD | 1 TB | 931 GiB | USB | Cold-Tier (archived, Backup) | JA |

Dateisystem: durchgehend ext4. Kein LUKS auf irgendeinem Medium.

Extern gesamt: SSD (238 GiB) + HDD (931 GiB) = 1169 GiB
Gesamt (alle Medien): 238 + 476 + 238 + 931 = 1883 GiB

### Tier-Logik (verbindlich, Nachtrag 2026-10-04)

Vier unabhaengige Ziele, kein gestuftes Wandern:

| Tier | Medium | Was liegt drauf | Live | Deep |
|---|---|---|---|---|
| Hot | Externe SSD | SQLite, KuzuDB, aktive Indizes | rw | rw |
| Warm | SD (Deck-Slot) | latente Daten, grosse Vektor-Sets, vorbereitete Indizes | r | w |
| Cold | Externe HDD | alles archived, Backups, zstd-Dumps | r | w |
| Minimal | Interne NVMe | Code, Config, Modelle | rw | rw |

Regeln:
- `archived` geht immer auf HDD. Keine Zwischenstufe.
- SD = Lese-Archiv fuer seltene, aber nuetzliche Daten.
- Live liest (r), Deep schreibt (w) - auf SD und HDD.
- NVMe traegt keine DB.
- Kein LUKS. Extern ist Wegwerfware, Lebensdauer nebensaechlich.
- Auto-Mount fuer SSD, SD, HDD (fstab: nofail, noatime).

### Regel zur Modellablage

- Aktive Modelle (Streaming, taeglicher Einsatz): NVMe
- Archiv-Modelle (selten): SD
- Modelle, die streamen sollen: immer NVMe
- SD ist fuer DB-Warm erlaubt, fuer Modelle nur Ablage

### Praktisch erreichbar
- Ziel heute: A2 (50 GB, alle wichtigen Modelle + Docs)
- A3 nach gpt-oss-20b Download
- A4 wenn The Stack gefiltert vorliegt
- A5 wenn SD vollstaendig belegt

### Regel
- Hoehere Stufe = mehr Autonomie, aber mehr Pflegeaufwand.
- A1 ist Standard. A2 ist Wunsch. A3+ nur wenn tatsaechlich genutzt.

### Hardware-Optimierung (Nachtrag 2026-09-30)

- Cooling: PTM7950, bessere Luft
- TDP: 15 W Standard, bis ~23 W moeglich
- GPU-OC: +25 % moeglich, aber zweitrangig

Reihenfolge: UV -> RAM -> Cooling -> TDP -> GPU -> CPU.
Metrik: Tokens/Joule statt Peak-MHz.

Thermik: Eine Zone, luefterlos unter 60 C.

### MCP-Zugriffsschicht (Nachtrag 2026-10-04)

MCP verbindet externe LLMs (Tablet, DeepSeek web) mit dem System.

**Regel: Nur lesend.** Kein Schreibzugriff von aussen.

**Drei Server (lokal, stdio):**

| Server | Was |
|---|---|
| Doku-Server | Schema, Meta-Regeln, Kontext-Ausschnitt |
| SQLite-Lese-Server | SELECT auf freigegebene Tabellen |
| KuzuDB-Lese-Server | Graph-Traversal, Vektor-Suche |

**Transport:**
- Lokal (Deck): stdio, kein Netzwerk
- Extern (Tablet): Streamable HTTP + Auth + TLS + Reverse Proxy

**Kein Schreibzugriff.**
Der einzige DB-Schreiber ist Deep Mode auf dem Deck.
Externe LLMs liefern Vorschlaege als Text zurueck.
Deep prueft, erzeugt Meta-Ebenen, schreibt.

**Sicherheit:**
- Live-MCP-Server: read-only
- Deep-MCP-Server: gar nicht exponiert
- Keine Secrets im Server
- Input-Validierung pro Tool

**Wann direkt statt MCP:**
Bulk-Ingest, Migration - Python-API schneller als MCP.
MCP fuer interaktive, explorative Abfragen.

## 22. Zwei-Phasen-Modell (Nachtrag 2026-10-04)

### Kernidee

**Live schreibt roh. Deep verdaut.**

| Phase | Was passiert | Wo |
|---|---|---|
| Live | schnell ablegen, Telemetry sammeln | SQLite (raw) |
| Deep | verdauen, Meta-Ebenen erzeugen, Graph/Vektor bauen, Tiers verteilen | alle Engines |

### Live Mode

- liest aus vorbereitetem Zustand
- schreibt nur raw nach SQLite (schnell, Append)
- sammelt Telemetry: task_id, task_type, model_id, role,
  duration_ms, outcome, error_type, fallback_used, tokens_in/out
- kein Graph-Update, keine Vektor-Berechnung, keine Reindexierung
- fasst KùzuDB nur lesend an

### Deep Mode

- verdaut rohe Eintraege
- erzeugt Meta-Ebenen (derived, verified, conflict, archived)
- baut Graph + Vektor in KuzuDB
- verteilt Tiers: archived -> HDD, latentes -> SD
- verarbeitet Telemetry: aggregated, pattern, recommendation
- einziges Schreib-Organ des Systems

### Der Speedup

Weil KuzuDB seine Indizes beim Schreiben optimiert (HNSW, CSR),
sind Live-Abfragen nach jedem Deep-Run schneller als davor.
Ohne Deep wuerde Live auf unoptimierten Rohdaten suchen.

### Konsequenz

- Live: schnell, weil es nur liest und anhaengt
- Deep: effizient, weil es autonom und in der Nacht arbeitet
- Nach jedem Deep-Run: Live schneller
- Kein Konflikt zwischen laufender Arbeit und Migration/Backup

### Was nicht passiert

- Live entscheidet nie gegen das Konzept.
- Deep loescht nie ohne Backup.
- Deep bricht nie mitten in einer Transaktion ab (Snapper-Punkt abwarten).
- Kein zweiter DB-Schreiber. Nur Deep.
